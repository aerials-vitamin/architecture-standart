# FURPS+ Requirements Table for Standard Bank Deposit Digitalization

| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | **Функциональные (Functionality)**  |              |
|     | F1. Отображение списка доступных депозитов с актуальными ставками на сайте для новых клиентов | Архитектурно значимое требование, так как потребует интеграции данных из внутренних систем на внешний сайт |
|     | F2. Возможность подачи заявки на сайте с указанием номера телефона и Ф.И.О. | |
|     | F3. Отображение списка доступных депозитов с актуальными ставками в интернет-банке для существующих клиентов | |
|     | F4. Отображение персонализированных ставок в интернет-банке | Требует доступа к данным клиента и расчета индивидуальных ставок |
|     | F5. Возможность подачи заявки на открытие депозита в интернет-банке с указанием счета и суммы | |
|     | F6. Подтверждение операции открытия депозита через СМС-код | Интеграция с существующим функционалом ядра системы |
|     | F7. Возможность обработки заявок на депозит сотрудниками бэк-офиса в АБС | На этапе MVP сохраняется ручная обработка |
|     | F8. Отправка СМС-уведомлений клиенту после подтверждения ставки и открытия депозита | Требует интеграции с СМС-шлюзом |
|     | F9. Система хранения и управления ставками по депозитам | Архитектурно значимое требование, так как требуется создание нового функционала, который сейчас отсутствует в системах |
| U   | **Удобство использования (Usability)** |              |
|     | U1. Соответствие интерфейса принятой в компании системе дизайна | Необходимо обеспечить визуальную согласованность всех продуктов банка |
|     | U2. Использование фирменных цветов и брендированных элементов | |
|     | U3. Удобный интерфейс для клиентов | Неконкретное требование, которое требует уточнения с точки зрения UX/UI |
| R   | **Надёжность (Reliability)**           |              |
|     | R1. Доступность всех сервисов 24/7 с уровнем доступности 99,9% | Архитектурно значимое требование, так как потребует реорганизации инфраструктуры |
|     | R2. Обеспечение работоспособности интернет-банка в случае сбоев в ЦОД | Требует проработки схемы отказоустойчивости |
|     | R3. Обеспечение работоспособности АБС при увеличении нагрузки от онлайн-заявок | Архитектурно значимое требование, так как текущая база данных АБС уже перегружена |
| P   | **Производительность (Performance)**   |              |
|     | P1. Быстрый отклик по всем операциям (миллисекунды) | Архитектурно значимое требование |
|     | P2. Загрузка справочных данных в интерфейсе интернет-банка должна занимать меньше секунды | Требует оптимизации существующего процесса |
|     | P3. Равномерное горизонтальное масштабирование и распределение запросов между серверами, приложениями и ЦОД | Архитектурно значимое требование |
| S   | **Поддерживаемость (Supportability)**  |              |
|     | S1. Разработка документации для дальнейшего расширения системы | |
|     | S2. Обеспечение возможности расширения функциональности в будущем (от MVP до полной автоматизации) | Архитектурно значимое требование |
|     | S3. Использование существующих технологий и экспертизы для разработки новых компонентов | |
| +R  | **+ Ограничения (Restricitions)**      |              |
|     | +R1. Использование существующих баз данных MS SQL и Oracle | Архитектурно значимое требование |
|     | +R2. Новые технологии должны быть совместимы с существующими платформами разработки | |
|     | +R3. Использование Kafka для очередей сообщений | Архитектурно значимое требование |
|     | +R4. Рассмотрение возможности перевода интернет-банка на микросервисную архитектуру в рамках задачи открытия депозитов | Архитектурно значимое требование |
|     | +R5. АБС может масштабироваться только вертикально из-за своей базы данных | Техническое ограничение, которое может повлиять на архитектурные решения |
|     | +R6. Избежание прямой работы интернет-банка с API АБС в новом процессе | Архитектурно значимое требование |
|     | +R7. Шифрование трафика при передаче чувствительных данных с сайта и в интернет-банке | Требования безопасности |
|     | +R8. Разделение доступа к данным между сотрудниками депозитов и кредитов по требованиям безопасности | Дополнительное требование, выведенное из описания текущего процесса |
|     | +R9. Избежание доработок ядра системы интернет-банка на стороне подрядчика | Архитектурно значимое ограничение |
|     | +R10. Реализация новой системы хранения ставок и доступа к ней с разных систем | Дополнительное требование, выведенное из описания текущего процесса |
